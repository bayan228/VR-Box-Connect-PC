# Протокол VR Box Connect v1: MONO и Stereo SBS

Спецификация реализуемого экспериментального видеотракта. Целые числа и
float32 передаются little-endian, JSON в UTF-8. Magic `0x5652` имеет байты
`52 56`, а не ASCII-последовательность `56 52`.

Один Android-клиент получает H.264: рабочий стол или тестовый шаблон MONO,
синтетический SBS либо стереокадр композитора SteamVR. Размещение глаз
согласуется явно; MONO не превращается в два независимых ракурса.
Wire-формат v1 не изменён: возможности SBS и Recenter расширяют JSON control.
Локальный IPC между драйвером SteamVR и сервером не передаётся по этому протоколу.
Ранний skeleton с несовместимыми размерами структур и ошибочной CRC не поддерживается.

## 1. Сессия и безопасность

- TCP: ПК слушает `8765`.
- UDP: ПК принимает timing/NACK и отправляет видео с `8766`, принимает IMU на `8767`.
- Discovery: ПК отвечает на UDP `8768`; приложение пока использует ручной IP.
- Клиент заранее привязывает два UDP-сокета к свободным локальным портам и
  сообщает `video_port` и `imu_port` в HELLO. Адрес берётся из TCP-соединения,
  не из JSON. Сервер принимает UDP только с зарегистрированной пары IP/порт.
- Поддерживаются числовые IPv4: RFC1918, loopback и link-local. DNS, STUN,
  облако и переадресация через интернет не используются.
- HELLO требует шестизначный PIN, показанный локально сервером. Неверный
  PIN закрывает соединение; следующая попытка возможна через одну секунду.
- Одновременно разрешена одна сессия. Для HELLO даётся три секунды;
  отсутствие TCP-трафика десять секунд завершает сессию. Клиент отправляет
  TCP ping раз в секунду. После SESSION_END сервер продолжает слушать.
- PIN не заменяет шифрование: TCP, видео и IMU передаются открыто. Режим
  предназначен только для доверенной локальной сети. Не открывать порты в интернет.

## 2. Общий UDP-заголовок

| Смещение | Размер | Поле |
|----------|--------|------|
| 0 | 2 | magic = 0x5652 |
| 2 | 1 | version = 1 |
| 3 | 1 | channel: 1 video, 2 IMU, 3 timing, 4 NACK |
| 4 | 1 | flags, в текущем потоке 0 |
| 5 | 1 | reserved = 0 |
| 6 | 4 | sequence, счётчик датаграмм канала с оборотом uint32 |
| 10 | 2 | payload_len |
| 12 | 2 | CRC16 заголовка bytes[0..11] |
| 14 | N | payload |

CRC16-CCITT-FALSE: poly `0x1021`, init `0xFFFF`, без отражения битов,
xorout `0`. Контрольный результат для ASCII `123456789`: `0x29B1`.
Реализации: `pc-server/src/protocol/protocol.cpp` и Android `Protocol.kt`.

Общий размер датаграммы не более **1200 байт**, включая оба заголовка.
`payload_len` должен точно совпадать с принятым размером после общего
заголовка; обрезанные пакеты и лишние байты не допускаются. Неверные CRC,
версия, канал, reserved и неизвестные flags отбрасываются.

Зарезервированный `flags.bit0` означает последние два байта payload с CRC16
его предшествующих байтов. C++-парсер умеет проверять и удалять эту CRC.
Android текущего этапа явно отвергает такие пакеты. Оба отправителя используют
`flags=0`; согласования дополнительных flags пока нет.

## 3. Видео

В начале video payload находится ещё один заголовок длиной 16 байт.
Смещения ниже отсчитываются от начала payload, то есть от байта 14 датаграммы.

| Смещение | Размер | Поле |
|----------|--------|------|
| 0 | 2 | frag_index, начиная с 0 |
| 2 | 2 | frag_total |
| 4 | 4 | frame_id |
| 8 | 1 | codec = 0 (H.264) |
| 9 | 1 | frame_type: 0 IDR, 1 P |
| 10 | 1 | reserved = 0 |
| 11 | 1 | nal_type_hint: 5 IDR, 1 P |
| 12 | 4 | frame_ts_ms, время захвата относительно начала видеосессии |
| 16 | N | фрагмент полного Annex B access unit |

Один `frame_id` обозначает **целый AU**, включая все его NAL со старт-кодами
`00 00 01` или `00 00 00 01`. Это не отдельный NAL. Все фрагменты AU имеют
одинаковые метаданные, кроме `frag_index` и общей UDP sequence.

Максимум данных фрагмента: `1200 - 14 - 16 = 1170` байт. Лимит AU: 2 MiB,
лимит `frag_total`: 2048. Пустые фрагменты, индексы вне диапазона,
несогласованные метаданные и превышение лимитов не принимаются.

Сервер начинает `frame_id` с 0 и увеличивает его для каждого AU. При
переполнении действует арифметика uint32. Каждый IDR содержит SPS и PPS
перед изображением. Отдельные пакеты config/SEI и H.265 в текущем режиме
не передаются. B-кадры отключены; обычный GOP равен одной секунде.

Клиент ограничивает память и время сборки, допускает перестановку и
дубликаты фрагментов. При потере AU, пропуске frame_id или переполнении
очереди зависимые P-кадры отбрасываются до следующего IDR. Запрос IDR
ограничивается по частоте (не чаще одного раза в 500 мс). Исправный декодер
не сбрасывается при каждом обычном IDR.

Основной способ восстановления: TCP `keyframe_request` (0x0C). Сервер
также поддерживает NACK (channel 4), трактуя его как запрос нового IDR,
а не как запрос повторной отправки старых фрагментов:

| Смещение payload | Размер | Поле |
|------------------|--------|------|
| 0 | 4 | frame_id |
| 4 | 2 | frag_count; 0 означает весь кадр |
| 6 | 2*N | frag_index[] |

## 4. TCP Control

| Смещение | Размер | Поле |
|----------|--------|------|
| 0 | 2 | magic = 0x5652 |
| 2 | 1 | version = 1 |
| 3 | 1 | msg_type |
| 4 | 4 | payload_len, максимум 65536 |
| 8 | N | UTF-8 JSON; только ping имеет бинарное тело |

TCP может разбивать сообщение на произвольные части или объединять
несколько сообщений. Отправитель дописывает весь буфер; приёмник сначала
получает заголовок, проверяет размер, затем читает тело. Ошибочный фрейминг
закрывает соединение, а не вызывает бесконечный поиск нового magic.

| Код | Имя | Направление | Содержание |
|-----|-----|-------------|------------|
| 0x01 | hello | клиент -> ПК | proto, pin, video_port, imu_port; device, layouts, display_rotation |
| 0x02 | hello_ack | ПК -> клиент | proto, codecs, max_res, ports, features |
| 0x03 | settings_request | клиент -> ПК | codec и предпочтительные параметры видео |
| 0x04 | settings_ack | ПК -> клиент | параметры видео, imu_rate_hz либо recentered/reason |
| 0x05 | video_start | ПК -> клиент | фактические параметры видео |
| 0x06 | video_stop | ПК -> клиент | {} |
| 0x07 | imu_start | клиент -> ПК | {"imu_rate_hz":100} |
| 0x08 | imu_stop | клиент -> ПК | {} |
| 0x09 | telemetry | ПК -> клиент | fps, br_kbps, capture_encode_ms, imu_samples |
| 0x0A | client_telemetry | клиент -> ПК | необязательная статистика |
| 0x0B | error | ПК -> клиент | code, msg |
| 0x0C | keyframe_request | клиент -> ПК | {} |
| 0x0D | session_end | любая сторона | reason необязателен |
| 0x0E | ping | клиент -> ПК -> клиент | ровно 8 байт u64, эхо без изменений |
| 0x0F | recenter | клиент -> ПК | {}; ответ SETTINGS_ACK {"recentered":true/false} |

Пример HELLO:

```json
{"proto":1,"device":"Android","pin":"123456","video_port":49160,"imu_port":49161,"layouts":["mono","stereo_sbs"],"display_rotation":90}
```

Пример HELLO_ACK:

```json
{"server":"VR Box Server","proto":1,"codecs":["h264"],"max_res":[1280,720],"ports":{"tcp":8765,"video":8766,"imu":8767},"features":[]}
```

Пример фактических параметров:

```json
{"codec":"h264","width":1280,"height":720,"fps":30,"bitrate_kbps":8000,"gop_s":1,"b_frames":0,"resilience":1,"layout":"mono","source":"desktop","encoder":"media_foundation_software"}
```

Для SBS HELLO обязан содержать `layouts` с `stereo_sbs`; отсутствие поля
считается поддержкой только MONO. Старый клиент отвергается в SBS-режимах,
но продолжает работать с MONO. Выбранное размещение приходит в видео SETTINGS_ACK
и VIDEO_START, а не в HELLO_ACK.
Для SteamVR также нужен `display_rotation` 90 или 270 градусов: это ориентация
экрана Android, а не угол поворота изображения в калибровке.

SBS SETTINGS_ACK и VIDEO_START содержат `layout: "stereo_sbs"`.
`width` и `height` относятся ко всему SBS, не к одному глазу. По этому layout
клиент вычисляет левую половину `x: 0..0.5`, правую `x: 0.5..1` и пропорции
одного глаза `(width/2)/height`. Отдельные rect/aspect поля по сети не передаются.
Источник имеет значение `test_pattern` или `steamvr`; в SteamVR HELLO_ACK
объявляется `features: ["recenter"]`. IPD и FOV задаются локальным CLI и
передаются драйверу через IPC, а не через видео JSON. MONO не объявляет Recenter.

Параметры CLI сервера определяют профиль. Запрос клиента не может изменить
их произвольно. Клиент обязан использовать SETTINGS_ACK, а не размеры,
которые он запросил. ACK и VIDEO_START отправляются **после успешного
открытия** источника и кодировщика; передача UDP включается после этих сообщений.
Для `source: "steamvr"` это означает готовность IPC и кодировщика, а не наличие
первого кадра композитора. Клиент запускает IMU, ping и control сразу после
VIDEO_START, до декодирования первого кадра. Отсутствие кадров SteamVR не
переключает источник на рабочий стол и не вызывает отправку выдуманного видео.
Повторный SETTINGS_REQUEST требует переподключения. После IMU_START
приходит отдельный SETTINGS_ACK `{"imu_rate_hz":100}`, без video-полей.

Диапазоны профиля: чётная ширина 160..1920, чётная высота 120..1080,
fps 1..60, bitrate_kbps 100..50000. Практический стартовый профиль:
1280x720, 30 fps, 8000 kbit/s. Источник `test_pattern` не читает рабочий стол.
Для SBS ширина кратна четырём, чтобы каждый глаз имел чётную ширину в NV12.
SteamVR по умолчанию использует 60 fps, 12000 kbit/s, IPD 64 мм, вертикальный
FOV 75 градусов. Изменение геометрии/fps требует перезапуска SteamVR и сессии.

Ошибки: 1 wrong_version, 2 bad_magic, 3 unsupported_codec,
4 unsupported_resolution, 5 buffer_overflow, 6 sensor_unavailable,
7 encoder_error, 8 session_busy, 9 authentication_failed, 10 invalid_request.
Не все коды требуются текущей реализации. Ошибка завершает клиентскую сессию.

## 5. IMU

Header payload: **16 байт**, затем `sample_count * 40` байт.

| Смещение payload | Размер | Поле |
|------------------|--------|------|
| 0 | 8 | timestamp_ns, монотонное время датчика на телефоне |
| 8 | 4 | sample_seq |
| 12 | 1 | sample_count, 1..24 |
| 13 | 1 | sample_format = 0 |
| 14 | 2 | reserved = 0 |
| 16 | 40*N | samples |

Семпл: 10 float32: quaternion `x,y,z,w`, gyro `x,y,z` в rad/s, accel
`x,y,z` в m/s². Android отправляет свежие реальные измерения примерно до
100 Гц. Отсутствие датчика не заменяется выдуманными движениями.

Сервер проверяет размеры, конечность чисел, норму кватерниона и порядок
sample_seq. Пакеты принимаются только после IMU_START. В MONO и синтетическом
SBS они учитываются, но не управляют игровой камерой. В `--steamvr` ориентация
и гироскоп преобразуются из координат телефона в OpenVR с учётом
`display_rotation`, нормализуются и передаются драйверу как 3DoF pose.
Позиционный трекинг не вычисляется из акселерометра: положение головы фиксировано.

Свежесть pose ограничена 250 мс по времени приёма на ПК. Повреждённый кватернион,
повторный или устаревший семпл не становится валидным трекингом. При потере IMU
предсказание по старой угловой скорости прекращается. TELEMETRY в SteamVR-режиме
дополнительно содержит `head_tracking` и `steamvr_frames` текущей сессии.

RECENTER принимается только при свежей pose: текущая ориентация становится
нейтральной, ответ `recentered: true`. Если данных нет или они устарели,
возвращается `false`, а старое начало координат сохраняется. Это ориентационное
центрирование, не настройка комнаты или измерение высоты. IMU_STOP аннулирует
pose; отключение и новый клиент сбрасывают состояние трекинга и Recenter.

## 6. Timing и метрики

Timing payload: **14 байт** (`u64 send_ns`, `u32 seq`, `u16 reserved=0`).
Клиент отправляет его примерно каждые 100 мс через свой video UDP-сокет.
Сервер возвращает датаграмму с неизменёнными байтами. RTT вычисляется
по монотонным часам самого клиента. Сервер не инициирует встречные эхо-циклы.

`frame_ts_ms` и `send_ns` принадлежат разным шкалам времени. Вычитание
времени ПК из времени телефона недопустимо. RTT не является задержкой
motion-to-photon. FPS отправки, декодирования и вывода также не тождественны.
Сервер сообщает суммарное время capture+encode, не выдавая его за отдельное
время кодировщика. Гарантии 10..33 мс у этого этапа нет.

Общий golden vector C++/Kotlin: `send_ns=0x0102030405060708`,
`seq=0x0A0B0C0D`, channel=3, header sequence равна seq:

```text
52 56 01 03 00 00 0D 0C 0B 0A 0E 00 A7 F5
08 07 06 05 04 03 02 01 0D 0C 0B 0A 00 00
```

## 7. Discovery

Отдельный формат, без общего 14-байтного UDP-заголовка:
`u16 magic`, `u8 version`, `u8 type`, `u16 payload_len`, затем payload.
Request type=0x10, payload содержит необязательное имя устройства до 64 байт.

Response type=0x11. Payload: `u16 protocol_version`, `u16 tcp_port`,
`u16 video_port`, `u16 imu_port`, `u32 codec_mask`, `u8 name_len`, затем
UTF-8 имя сервера. Фиксированная часть payload равна **13 байтам**.
`codec_mask=1` означает только H.264. Ответ отправляется unicast с
ограничением частоты. PIN в discovery не передаётся.

## 8. Минимальный обмен

```text
Client: bind UDP sockets -> TCP connect
Client -> Server: HELLO (PIN + bound UDP ports)
Server -> Client: HELLO_ACK
Client -> Server: SETTINGS_REQUEST
Server: open capture + encoder
Server -> Client: SETTINGS_ACK -> VIDEO_START
Client -> Server: timing (UDP), ping (TCP), IMU_START
Server -> Client: timing echo, ping echo, IMU SETTINGS_ACK
Client -> Server: IMU samples
Server -> Client: UDP IDR (SPS/PPS included) -> P frames, when capture is ready
Client -> Server: RECENTER, if advertised
Server -> Client: SETTINGS_ACK {recentered:true/false}
Client -> Server: KEYFRAME_REQUEST on loss
Server -> Client: fresh IDR
Client -> Server: SESSION_END
Server: stop encoder, close client, continue listening
```

Шифрование, новый codec, FEC и дополнительные каналы требуют отдельного
согласования возможностей или следующей версии протокола. Факт получения
SBS не доказывает комфортную задержку или совместимость конкретной игры.
