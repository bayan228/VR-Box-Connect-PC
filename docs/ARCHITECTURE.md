# Архитектура VR Box Connect

## Текущий этап

Desktop Preview MONO сохранён как независимый режим. Добавлены синтетический
SBS и экспериментальный драйвер SteamVR: виртуальный HMD, стереокадры
композитора и 3DoF от телефона. Это ещё не проверенный игровой шлем:
контроллеров, позиционного трекинга, аудиоканала и измеренной задержки нет.

```text
Windows primary desktop              Synthetic test pattern
        |                                     |
        v                                     |
DXGI Desktop Duplication                      |
        |                                     |
BGRA staging -> scale/letterbox -> NV12 <------+
        |
Media Foundation H.264 (software, baseline, no B frames)
        |
Annex B AU -> bounded fragments -> UDP :8766
        |
Android: reassembly -> bounded decoder queue -> MediaCodec
        |
SurfaceTexture / external OES -> OpenGL -> MONO or independent SBS eye crops

SteamVR scene -> compositor -> IVRVirtualDisplay -> BGRA IPC -> NV12 encoder
Android SensorManager -> UDP :8767 -> validated 3DoF -> IPC -> HMD pose
Android TCP :8765 <-> PIN / settings / lifecycle / keyframes / telemetry
```

## Сервер

`main.cpp` содержит один сетевой цикл `select` для control, timing, IMU и
discovery. У одной активной сессии есть один `VideoWorker` (`std::jthread`).
Он владеет `VideoSource`, COM, Media Foundation и DXGI на одном потоке.
Сессия останавливает и присоединяет этот поток до уничтожения сокетов и Winsock.
Ожидания сети/кадров ограничены; обработка SESSION_END не останавливает listener.

Захват не запускается при старте процесса: сначала требуется HELLO с верным
PIN и зарегистрированными UDP-портами, затем SETTINGS_REQUEST. Клиент получает
VIDEO_START только после успешного создания источника и кодировщика. Если
Windows сообщает ошибку захвата/кодирования, она передаётся клиенту, а не
маскируется обещанием работающего потока.
В SteamVR источник может быть готов до первого пикселя: VIDEO_START запускает
датчики и control телефона, затем кодировщик ждёт настоящий кадр композитора.
Ожидание видео не блокирует ping, IMU, Recenter или отключение.

DXGI выбирает основной монитор и его адаптер. BGRA-текстура копируется в
staging-память, поворачивается при необходимости и масштабируется в NV12 с
сохранением пропорций. При неизменном рабочем столе используется предыдущее
изображение. Отдельный аппаратный курсор пока не дорисовывается. При потере
доступа предпринимается повторное создание duplication; если оно неудачно,
сессия завершается с ошибкой и допускает переподключение.

Используется штатный синхронный H.264 MFT Windows. Это намеренно программная
базовая реализация без NVENC SDK, асинхронных аппаратных MFT и zero-copy.
При медленном кодировании старые кадры не накапливаются для последующего
пакетного воспроизведения. Размер AU ограничен 2 MiB. IDR содержит SPS/PPS,
поэтому декодер может восстановиться после потерь без отдельного config-канала.

Control JSON разбирается vendored `nlohmann/json` 3.11.3 (MIT). Размер
сообщения ограничен 64 KiB, вложенность ограничена, размеры/типы полей
валидируются. Проверка SHA256 зависимости выполняется CMake. Бинарный
протокольный модуль остаётся независимым от этой библиотеки.

## Драйвер SteamVR

Пакет `build/steamvr/vrbox` содержит `driver_vrbox.dll`, манифест и настройки.
OpenVR SDK закреплён на 2.15.6 с проверкой SHA256. Сервер с `--steamvr` запускается
раньше SteamVR; без живого сервера provider не регистрирует устройства.
`TrackedDeviceClass_DisplayRedirect` ставится в очередь **до HMD**. Это важно
для выбора виртуального пути вывода при активации HMD; обратный порядок на
SteamVR 2.17.9 давал зарегистрированный шлем без вызовов `Present`.

HMD предоставляет `IVRDisplayComponent`: размер одного глаза, два viewport,
проекции, IPD и тождественную distortion. Отдельный redirect предоставляет
`IVRVirtualDisplay`; свойства наличия компонентов выводит сам OpenVR.
Искажение линз применяется только в калиброванном рендерере телефона.
Задержка redirect добавляется к HMD, поэтому прибавка 40 мс задана только
redirect-у; это оценка, не измеренная motion-to-photon задержка.

`Present` открывает D3D11 shared texture на совместимом адаптере, проверяет
полный SBS-размер и формат RGBA/BGRA8, использует keyed mutex при наличии и
ставит GPU-копирование в staging. `WaitForPresent` завершает GPU-readback и
публикует BGRA. Одновременно хранится не более одной незавершённой копии.
Кэш текстур ограничен; старые копии после задержки GPU не выдаются за свежие.
Часы виртуального vsync монотонны и продолжают идти без новых кадров.

Control/pose и пиксели имеют отдельные shared mappings и mutex: копирование
кадра не держит блокировку трекинга. Владелец IPC один, heartbeat живёт 2 с,
pose 250 мс, опубликованный кадр 500 мс. Поколение сессии не позволяет прочитать
пиксели предыдущего клиента после reconnect или смены владельца. Драйвер
проверяет поколение повторно после GPU-копирования; рабочий стол не является
резервным источником SteamVR.

Ориентация и гироскоп преобразуются с учётом landscape 90/270 и Recenter.
Android передаёт активный кватернион device-to-world. Перед центрированием
используется `q_mounted = q_sensor * Rz(-display_rotation)`: при ROTATION_90
ось экрана X равна минус device Y, ось экрана Y равна device X. Противоположный
знак давал разворот базиса на 180 градусов и инвертировал yaw/pitch.
Гироскоп преобразуется тем же исправленным базисом, затем в систему Recenter;
кватернион целиком не инвертируется и изображение не зеркалится.
Соглашение сверено с [AOSP SensorManager.remapCoordinateSystem](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-14.0.0_r1/core/java/android/hardware/SensorManager.java).
Высота головы фиксирована в 1.2 м; движение по комнате не имитируется.
`poseTimeOffset` отражает возраст последнего приёма на ПК, не синхронизацию
часов датчика и ПК. При потере свежей IMU pose невалидна, угловая скорость
для предсказания нулевая. Поток обновления pose останавливается до освобождения IPC.

## Android

Жизненный цикл принадлежит Activity, а не отдельному незапускаемому service.
Сеть, датчики и декодирование работают не на UI-потоке. Отключение, уход
в фон и уничтожение экрана закрывают сессию. Ресурсы декодера освобождаются
до освобождения его Surface; GL-операции выполняются на GL-потоке.

UDP-сокеты привязываются до HELLO и подключаются к конкретным портам ПК.
Сборка AU ограничена числом кадров, байтами и сроком ожидания. Пропуск
кадра или переполнение очереди переводит декодирование в ожидание нового
IDR; запросы IDR ограничены по частоте. Нормальный IDR не является поводом
для постоянного flush декодера.

MediaCodec получает полный Annex B AU и выводит в SurfaceTexture.
Рендер использует external OES texture и матрицу SurfaceTexture, а не
`GL_TEXTURE_2D`. В MONO один кадр повторяется в двух viewport. В SBS каждый
глаз использует только свой согласованный rect и пропорции одного глаза;
калибровка не смешивает соседние половины. Это не реконструкция объёма из MONO.

SensorManager передаёт реальные измерения ориентации, гироскопа и
акселерометра. Отсутствие датчика не должно имитировать трекинг.
В SteamVR-режиме эти данные обновляют HMD через сервер и локальный IPC.
В остальных режимах остаётся только счётчик IMU. Инъекции мыши и подмены
не-VR игровой камеры нет. Датчики запускаются до первого декодированного кадра.

## Метрики

- UDP RTT измеряется по собственным монотонным часам телефона.
- FPS отправки берётся из реально отправленных AU на сервере.
- FPS декодирования и вывода считаются отдельно на клиенте.
- `capture_encode_ms` является суммарным временем двух этапов на ПК.

Часы устройств не синхронизированы. RTT/2 и сумма нескольких средних
не доказывают motion-to-photon: ещё есть очереди декодера/композитора,
ожидание vsync, развёртка дисплея и задержка датчика. Числа 10..33 мс
остаются целевым ориентиром, а не измеренным результатом этого проекта.

## Проверка

`protocol_tests` проверяет CRC, общий C++/Kotlin golden vector, размеры
структур, повреждения, усечения, предельные длины и discovery.
`video_tests` проверяет MONO, синтетический SBS и SBS через IPC: H.264
SPS/PPS/IDR, сохранение времён захвата, отсутствие дубликатов и порядок глаз
после декодирования Media Foundation. Захвата экрана нет.
`head_pose_tests` проверяет координаты, нормализацию, Recenter и свежесть IMU.
`steamvr_bridge_tests` проверяет владение, блокировки, pitch, свежесть и поколения.
`steamvr_driver_tests` использует mock OpenVR host и настоящие D3D11 textures;
проверяет GPU-readback, регистратор, раздельные глаза, vsync и завершение.
Без аппаратного D3D11 этот последний тест явно пропускается с кодом 77.
`session_smoke.ps1` проверяет MONO, SBS и ожидание SteamVR отдельными режимами:
handshake, framing, pairing, UDP, IMU, keyframe и повторные сессии.

Дополнительно выполнен ручной тест на установленном SteamVR 2.17.9 и RTX 3050:
отдельная scene application отправляла разные текстуры глаз через настоящий
`IVRCompositor::Submit`, а loopback-клиент передавал тестовую IMU и принимал H.264.
Проверены реальные callbacks, чтение SBS и правильный порядок цветов глаз.
Использован отдельный `VR_PATHREG_OVERRIDE`, конфигурация/логи в `.build-tmp`;
глобальный список драйверов не изменялся. Это не запуск игры на телефоне.

Android unit-тесты проверяют чистую Kotlin-логику протокола, сборки и очередей.
Физический телефон нужен для проверки MediaCodec, SurfaceTexture, датчиков,
нагрева и поведения Wi-Fi. Сборка APK требует готового JDK/Gradle/SDK;
состояние в текущем окружении описано в README, не подменяется статическим анализом.

## Дальнейшие этапы

1. Собрать APK и проверить этот тракт на реальном телефоне, включая потери
   Wi-Fi, повторные подключения, сворачивание и смену ориентации.
2. Профилировать capture/encode/decode/render; внедрить GPU-конверсию и
   аппаратный кодировщик на основе результатов, а не предположений.
3. Проверить уже имеющуюся калибровку на конкретных линзах и измерить полную
   задержку. Не называть смещение картинки физически измеренным IPD.
4. Проверить SteamVR на физическом телефоне и в выбранных seated-играх,
   настройку origin/комнаты, длительную работу, reconnect и отказ GPU.
5. Отдельно решить контроллеры, позиционный трекинг, звук, защищённый transport
   и release-подпись. FEC и динамическое качество добавлять после замеров.
